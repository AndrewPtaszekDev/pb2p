# pb2p

`pb2p` automates a two-peer [Proxmox Backup Server](https://www.proxmox.com/en/proxmox-backup-server)
(PBS) deployment. Two Proxmox VE hosts each run a PBS instance for the other,
so each peer gets off-site, encrypted backups on the other's hardware.

On each host, `pb2p`:

1. Carves out an LVM logical volume and builds a ZFS pool and dataset on it.
2. Creates a Debian LXC container with the dataset bind-mounted in.
3. Installs PBS in the container, creates a datastore with prune and verify
   jobs, and creates a backup user and API token for the peer.
4. Writes a peer config file containing everything the other host needs to
   connect.

The other host then runs `pb2p peer <file.yaml>` with that file to register the PBS
instance as a storage target in Proxmox VE.

Every step checks existing state first, so commands are safe to re-run.

## Requirements

- A Proxmox VE host, run as `root`.
- An LVM volume group named `pve` with enough free space for the logical volume
  (change `zfs.lvsize` as needed).
- Network access from the container to `download.proxmox.com` and
  `enterprise.proxmox.com`.
- Network connectivity between the two peers (e.g. via WireGuard).

## Building

The tool runs on the Proxmox host, so build for linux:

```sh
GOOS=linux GOARCH=amd64 go build -o pb2p .
scp pb2p root@<proxmox-host>:/usr/local/bin/
```

## Usage

`pb2p` reads and writes files in the current working directory, so run it
from the directory where you want `config.yaml` and the peer config to live.

### 1. Provision the server

Generate a default config:

```sh
pb2p config
```

Edit `config.yaml` and fill in the required values (see
[Configuration](#configuration)), then run the full setup:

```sh
pb2p server
```

`server` runs `config`, `zfs`, `container`, and `pbs` in order. Each step can
also be run on its own.

When it finishes, a peer config file named after `pbs.peer_username` is written
to the current directory.

### 2. Hand off the peer config

Send the peer config file to your peer over a secure channel — it contains an
API token secret. Before they use it, the `ip` field must be set to the address
where they can reach your PBS container (e.g. your WireGuard address).

### 3. Register the peer's PBS

On the receiving host:

```sh
./pb2p peer /path/to/peer-config.yaml
```

This adds the remote PBS datastore as Proxmox VE storage (named `peer-pbs`)
using `pvesm add pbs`.

## Commands

| Command            | Description                                                                 |
| ------------------ | --------------------------------------------------------------------------- |
| `config`           | Write a default `config.yaml`. An existing file is left untouched.          |
| `zfs`              | Create the LVM logical volume, zpool, and dataset (`compression=lz4`, `atime=off`). |
| `container`        | Download the template if needed, create the container, attach the bind mount, and start it. |
| `pbs`              | Install PBS in the container, create the datastore, jobs, user, token, and ACLs, then write the peer config. |
| `server`           | Run `config`, `zfs`, `container`, and `pbs` in sequence.                    |
| `peer <file>`      | Register a peer's PBS storage on this host from their peer config.          |

## Configuration

`config.yaml` (generated by `pb2p config`):

```yaml
pbs:
  peer_username:        # required, recommended: PEERFIRSTNAME
container:
  ctid:                 # required, an unused CTID e.g. 101
  hostname: pbs
  template: debian-12-standard_12.12-1_amd64.tar.zst
  template_storage: local
  container_storage: local-lvm
  root_disk_gb: 8
  cores: 1
  memory_mb: 512
  ip:                   # required, CIDR e.g. 192.168.1.20/24
  gateway:              # required, e.g. 192.168.1.1
  password:             # required, container root password
zfs:
  lvsize: 500G
  lvname: zfs-store
  pool_name: tank
  dataset_name:         # required, recommended: PEERLASTNAME-backups
```

`config.yaml` contains the container root password and is git-ignored.

### What gets created

With the defaults above, a peer named `alice` and dataset `smith-backups`:

| Resource          | Value                                                      |
| ----------------- | ---------------------------------------------------------- |
| Logical volume    | `/dev/pve/zfs-store`                                       |
| ZFS pool          | `tank`, mounted at `/mnt/tank`                             |
| ZFS dataset       | `tank/smith-backups`                                       |
| Container         | privileged, `nesting=1`, bridged on `vmbr0`, `mp0` bind mount of `/mnt/tank/smith-backups` |
| PBS datastore     | `smith-backups`, daily garbage collection                  |
| Prune job         | `smith-backups-prune`, daily, keep last 7 / weekly 4 / monthly 3 |
| Verify job        | `smith-backups-verify`, daily, re-verify after 30 days     |
| PBS user & token  | `alice@pbs`, token `alice@pbs!backup-access`               |
| ACL               | `DatastoreBackup` on `/datastore/smith-backups` for the user and token |

### Peer config

The peer config written by `pbs` has the following fields:

```yaml
pbs_name: peer-pbs
ip: ""              # filled in before handing off
username: alice@pbs!backup-access
token_secret: ...
fingerprint: ...    # SHA-256 of the PBS TLS certificate
datastore_name: smith-backups
```

Your autogenerated encryption key is copied to the current directory for convienience.

[!warning] For the encryption key
> Copy and store it in at least two places that are not this Proxmox host. Without this key, encrypted backups are permanently unrecoverable.

## Project layout

```
main.go
cmd/                 Cobra commands
internal/
  config/            config.yaml and peer config loading, atomic file writes
  setup/             orchestration for each setup step
  zfs/               LVM and ZFS CLI wrappers
  pve/               pct, pveam, and pvesm wrappers
```
